# 知识库系统设计与实现方案

## 一、需求分析

### 1.1 核心需求
1. **用户认证系统**：账号密码登录
2. **三级层级结构**：团队空间 → 知识库 → 文章（父子级关系）
3. **可见性控制**：个人可见、团队成员可见、公开可见（支持继承）
4. **精细化权限管理**：精确到文章级别，支持只读、可编辑、管理员三种权限

### 1.2 业务场景
- 企业内部知识管理
- 部门协作文档管理
- 项目知识沉淀
- 团队知识共享

```sql
-- 团队空间表外键
ALTER TABLE team_spaces

-- 知识库表外键
ALTER TABLE knowledge_bases 
ADD CONSTRAINT fk_kb_team_space FOREIGN KEY (team_space_id) REFERENCES team_spaces(id) ON DELETE CASCADE,

-- 文章表外键
ALTER TABLE articles 
ADD CONSTRAINT fk_article_kb FOREIGN KEY (knowledge_base_id) REFERENCES knowledge_bases(id) ON DELETE CASCADE,
ADD CONSTRAINT fk_article_parent FOREIGN KEY (parent_id) REFERENCES articles(id) ON DELETE CASCADE,
ADD CONSTRAINT fk_article_author FOREIGN KEY (author_id) REFERENCES users(id) ON DELETE RESTRICT;

-- 团队成员表外键
ALTER TABLE team_members 
ADD CONSTRAINT fk_member_team_space FOREIGN KEY (team_space_id) REFERENCES team_spaces(id) ON DELETE CASCADE,
ADD CONSTRAINT fk_member_user FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE;

-- 权限表外键
ALTER TABLE permissions 
ADD CONSTRAINT fk_permission_user FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE,
ADD CONSTRAINT fk_permission_granted_by FOREIGN KEY (granted_by) REFERENCES users(id) ON DELETE SET NULL;

-- 文章版本表外键
ALTER TABLE article_versions 
ADD CONSTRAINT fk_version_article FOREIGN KEY (article_id) REFERENCES articles(id) ON DELETE CASCADE,
ADD CONSTRAINT fk_version_author FOREIGN KEY (author_id) REFERENCES users(id) ON DELETE RESTRICT;

-- 文章标签关联表外键
ALTER TABLE article_tags 
ADD CONSTRAINT fk_article_tag_article FOREIGN KEY (article_id) REFERENCES articles(id) ON DELETE CASCADE,
ADD CONSTRAINT fk_article_tag_tag FOREIGN KEY (tag_id) REFERENCES tags(id) ON DELETE CASCADE;

-- 评论表外键
ALTER TABLE comments 
ADD CONSTRAINT fk_comment_article FOREIGN KEY (article_id) REFERENCES articles(id) ON DELETE CASCADE,
ADD CONSTRAINT fk_comment_user FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE RESTRICT,
ADD CONSTRAINT fk_comment_parent FOREIGN KEY (parent_id) REFERENCES comments(id) ON DELETE CASCADE;
```

## 四、权限模型设计

### 4.1 权限继承规则
1. **默认继承**：创建知识库时默认继承团队空间的可见性；创建文章时默认继承知识库的可见性
2. **显式覆盖**：可以手动修改子资源的可见性，覆盖继承的可见性
3. **权限传递**：对团队空间有管理权限的用户，默认对该空间下的所有知识库和文章有管理权限

### 4.2 权限判断逻辑

**可见性判断优先级：**
1. 检查用户是否为资源创建者（所有者）
2. 检查权限表中是否有显式授权
3. 检查是否为团队成员（针对"团队成员可见"）
4. 检查资源可见性是否为"公开可见"
5. 检查父级资源的可见性和权限

**权限类型：**
- **只读（1）**：可以查看，不能编辑
- **可编辑（2）**：可以查看和编辑
- **管理员（3）**：可以查看、编辑、删除、授权他人

### 4.3 权限查询SQL示例

```sql
-- 检查用户对文章的权限
SELECT 
    p.permission_type,
    CASE 
        WHEN a.author_id = ? THEN 3  -- 作者默认有管理员权限
        WHEN p.permission_type IS NOT NULL THEN p.permission_type  -- 显式授权
        WHEN a.visibility = 3 THEN 1  -- 公开可见，默认只读
        WHEN a.visibility = 2 AND tm.user_id IS NOT NULL THEN 1  -- 团队成员可见
        WHEN a.visibility = 1 AND a.author_id = ? THEN 3  -- 个人可见，仅作者
        ELSE 0  -- 无权限
    END AS final_permission
FROM articles a
LEFT JOIN permissions p ON p.resource_type = 3 
    AND p.resource_id = a.id 
    AND p.user_id = ? 
    AND p.status = 1
LEFT JOIN team_members tm ON tm.team_space_id = (
    SELECT team_space_id FROM knowledge_bases WHERE id = a.knowledge_base_id
) AND tm.user_id = ? AND tm.status = 1
WHERE a.id = ? AND a.status > 0;
```

## 六、技术实现建议

### 6.1 后端技术栈
- **语言**：Java (Spring Boot) / Python (Django/FastAPI) / Node.js (Express/Nest.js)
- **ORM框架**：MyBatis / Sequelize / TypeORM / SQLAlchemy
- **认证**：JWT Token
- **缓存**：Redis（用户会话、权限缓存、热点数据）
- **搜索**：Elasticsearch（全文搜索）或MySQL全文索引
- **文件存储**：本地存储 / OSS（阿里云OSS、AWS S3）
- **消息队列**：RabbitMQ / Kafka（异步任务：邮件发送、通知推送）

### 6.2 前端技术栈
- **框架**：Vue.js / React / Angular
- **UI组件库**：Element UI / Ant Design / Material-UI
- **Markdown编辑器**：mavon-editor / tui-editor / Markdown-it
- **状态管理**：Vuex / Redux
- **路由**：Vue Router / React Router

### 6.3 数据库优化
- **读写分离**：主从复制，读操作走从库
- **分库分表**：如果数据量大，可按用户ID或团队空间ID分表
- **索引优化**：根据查询场景添加合适的索引
- **定期归档**：历史版本、旧日志归档到历史表

### 6.4 安全考虑
- **密码加密**：使用BCrypt或Argon2加密存储
- **SQL注入防护**：使用参数化查询
- **XSS防护**：内容输出时进行转义
- **CSRF防护**：使用Token验证
- **接口限流**：防止恶意请求
- **敏感操作日志**：记录所有权限变更、删除操作
- **数据备份**：定期全量备份 + 增量备份

## 七、可能遇到的问题与解决方案

### 7.1 权限性能问题
**问题**：权限判断逻辑复杂，频繁查询影响性能

**解决方案**：
- 使用Redis缓存用户权限（设置过期时间）
- 权限变更时清除相关缓存
- 优化权限查询SQL，使用联合查询减少数据库访问次数
- 考虑权限预计算，定期异步更新权限缓存

### 7.2 可见性继承的复杂性
**问题**：多层继承导致可见性判断逻辑复杂

**解决方案**：
- 在创建资源时显式存储最终可见性值（考虑继承后的实际值）
- 父级可见性变更时，触发子资源可见性重新计算（异步任务）
- 在权限表中冗余存储继承路径信息，便于查询

### 7.3 大文件存储问题
**问题**：文章内容、图片、附件占用存储空间大

**解决方案**：
- 文章内容存储在数据库，大文件（图片、附件）存储在对象存储服务
- 图片压缩和缩略图生成
- 定期清理未使用的附件
- 考虑CDN加速文件访问

### 7.4 并发编辑冲突
**问题**：多人同时编辑同一文章导致冲突

**解决方案**：
- 编辑锁定机制（进入编辑时锁定，离开时释放）
- 版本合并（类似Git的merge）
- 操作日志记录（支持操作撤销）
- 实时协同编辑（使用OT算法或CRDT）

### 7.5 全文搜索性能
**问题**：MySQL全文搜索性能有限，无法满足复杂搜索需求

**解决方案**：
- 使用Elasticsearch专门处理搜索
- 文章更新时同步到Elasticsearch
- 支持高级搜索：按标题、内容、标签、作者、时间范围组合查询
- 搜索关键词高亮显示

### 7.6 数据迁移与备份
**问题**：数据迁移困难，备份恢复耗时长

**解决方案**：
- 设计版本化的数据库迁移脚本
- 定期自动备份（每天全量，每小时增量）
- 支持按时间点恢复
- 测试环境定期同步生产数据（脱敏后）

### 7.7 权限管理的复杂性
**问题**：权限表数据量大，查询效率低

**解决方案**：
- 权限表按资源类型分区
- 定期清理过期权限记录
- 使用权限组（Role）概念，减少权限记录数量
- 权限继承算法优化，减少递归查询

### 7.8 通知系统的消息丢失
**问题**：通知可能丢失，用户体验差

**解决方案**：
- 使用消息队列保证消息可靠投递
- 消息持久化存储
- 失败重试机制
- 用户未读消息提醒

### 7.9 国际化支持
**问题**：多语言支持

**解决方案**：
- 数据库支持UTF-8编码
- 前端使用i18n国际化框架
- 内容多语言版本管理（可选功能）

### 7.10 移动端适配
**问题**：移动端访问体验差

**解决方案**：
- 响应式设计
- PWA支持（离线访问）
- 移动端APP（React Native / Flutter）
